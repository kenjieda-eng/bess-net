# projects body 焼き込み問題 — 根治可否の実査と設計案（Pj2-D 工程1・書込ゼロ）

**契機**: ユウ裁定 Pj2-C §4「規模から、**PATCH の洪水より根治を先に検討する**。テンプレ原型と完全一致する文に限り、表示時に field から再構成できれば、コード1箇所で全件根治・microCMS 書込ゼロ。キュレーション済み body を壊さない保守的判定が鍵」
**方式**: microCMS の projects **全 331 件を GET**（Pj2-C 実行後の最新）して機械判定。**本便の書込は裁定1の status 1フィールドのみで、本章の調査に伴う書込はゼロ**。

## 結論

**根治は可能。** 表示時再構成で **106 件（掲載中 47 件）の本文が field と一致**し、microCMS 書込はゼロ。
誤検出 0・冪等・非破壊を全 331 件で機械検査済み。加えて **取込器側の是正は不要**（現行の取込器はテンプレを生成していない＝過去の一括取込の遺物）。

## 1. テンプレ原型の特定

機械生成された body は次の形をしている（`pr-co70816-bess-3` の生 HTML より）:

```html
<h2 id="h3af4d147a9">プロジェクト概要</h2>
<p><strong>{name}</strong>は、{prefecture}{city}に立地する系統用蓄電所。
   [出力 {outputMw} MW 規模。][容量 {capacityMwh} MWh 規模。]
   発表企業：{operator}。ステータス：{status}（発表日：{cod}）。</p>
[<p>{PR のリード文}</p>]
<h2 id="h1b9eb7c3a9">出典</h2>
<ul>…</ul>
<p>※本ページは公開情報を構造化したものです。…</p>
```

**見出しの `id` が固定**（`h3af4d147a9` / `h1b9eb7c3a9`）である点が決定的な指紋。richEditor は見出しテキストから id を採番するため、同一テキストの見出しは同一 id になる（#122 で確認した挙動の副産物）。

## 2. テンプレ一致率（全 331 件）

| 分類 | 件数 | 判定条件 |
|---|---|---|
| **機械テンプレ（完全一致）** | **175** | body が固定見出しで**始まり**、かつ `発表企業：` を含む |
| キュレーション済み（不一致） | 140 | 上記に当たらない |
| body なし | 16 | — |

- 「body が固定見出しで**始まる**」= 175、「**含む**」= 175、「`発表企業：` を含む」= **175** — **3条件が完全に一致**。判定は堅い。
- **誤検出 0**: 175 件の第1段落に「定格出力／定格容量／受電／EPC／アグリゲーション業務」等のキュレーション痕跡は 1 件もない。
- 逆方向も 0: 固定見出しを持つのに第1文が非テンプレ、というレコードは 3 件あったが、いずれも**破損 city に「。」が含まれるため**正規表現が途中で切れていただけで、実体は機械テンプレ（`pr-co176308-bess`・`pr-afterfit-bess`・`pr-co96742-mie-8mwh`）。正規表現を `[\s\S]*?` にすれば 175 に含まれる。

### 紛らわしい 9 件（キュレーション側・触ってはいけない）

「〜に立地する系統用蓄電所**で、**」と続く手書き本文。`nc-nagahama-mikawacho`（body「滋賀県長浜市**三川町**」＝ field より詳しい）・`will-bungoono`・`taishi-bess` 等。
**固定見出しを持たないため判定条件で自動的に除外される。**

## 3. 表示時再構成の設計案

```ts
// src/lib/projects-body.ts（新規・約40行）
const TEMPLATE_HEAD = '<h2 id="h3af4d147a9">プロジェクト概要</h2>';
const LOCATION_SENTENCE = /(<p><strong>[^<]*<\/strong>)は、([\s\S]*?)に立地する系統用蓄電所。/;

/**
 * 取込器テンプレの所在地句を field から再構成する。
 * ★冪等: 再適用しても結果は変わらない（#119 の二重正規化事故を構造的に回避）。
 * ★保守的: 機械テンプレと確実に判定できる body 以外は原文をそのまま返す。
 */
export function reconstructProjectBody(p: Pick<Project, 'body' | 'prefecture' | 'city'>): string {
  const body = p.body ?? '';
  if (!body.startsWith(TEMPLATE_HEAD)) return body;   // 判定①
  if (!body.includes('発表企業：')) return body;        // 判定②（二重の確証）
  const m = LOCATION_SENTENCE.exec(body);
  if (!m) return body;                                 // 判定③
  const loc = `${p.prefecture ?? ''}${p.city ?? ''}`.trim();
  const sentence = loc
    ? `${m[1]}は、${loc}に立地する系統用蓄電所。`
    : `${m[1]}は系統用蓄電所。`;                        // 所在地不明なら句ごと落とす
  return body.slice(0, m.index) + sentence + body.slice(m.index + m[0].length);
}
```

### 配置（#119 対策）

`body` の消費箇所は **`src/app/projects/[slug]/page.tsx` の 3 箇所だけ**（`linkifyHTML` / `getRelatedEntities({baseBodyHtml})` / 条件レンダリング）。
ページ先頭で 1 回だけ適用し、以降は同じ変数を使う。

```ts
const item = await getProjectBySlug(params.slug);
if (!item) notFound();
const body = reconstructProjectBody(item);   // ← ここ1箇所だけ
```

`getProjectBySlug`（取得側）に置く案もあるが、**消費側が1ルートしかないため表示側1箇所で十分**。
なお本関数は冪等なので、将来どちらに移しても二重適用の事故は起きない（#119 の `normalizeSubstationPlace` は「原値を退避先に逃がす」設計だったため二重適用で原値が消えたが、本関数は退避を持たない）。

## 6. ★副次的発見: 破損は `<meta name="description">` にも出ている

meta description と JSON-LD は**既に `${prefecture}${city}` 由来**（body 由来ではない）。
つまり破損 city は検索結果に出る説明文にも入っている。本番実測:

```
/projects/pr-co161802-gifu
  <meta name="description" content="岐阜県【日本蓄電池株式会社】岐阜県岐阜市に所在する系統用蓄電池プロジェクト…">
/projects/pr-co168085-saga
  <meta name="description" content="佐賀県三崎未来ホールディングス、佐賀県伊万里市に所在する系統用蓄電池プロジェクト…">
/projects/pr-co176308-bess
  <meta name="description" content="広島県庄原市に所在する系統用蓄電池プロジェクト…">   ← Pj2-C の field 修正で既に正常
```

**A-1 の 21 件を直す優先度は、走査レポートで書いたときより高い**——被害は一覧の所在地列と本文だけでなく、**SEO で表示される説明文**にも及んでいる。
同時に、meta が既に field 由来である事実は、本設計（body も field 由来にする）が**既存コードと同じ思想**であることの裏づけでもある（#121 SSOT）。

### 選択肢（ユウの裁定を仰ぐ）

- **案 A（所在地句のみ）** … 本書 §3 の実装。106 件が変わる。裁定 §4 の仮説どおりの最小実装
- **案 B（第1文を全体再生成）** … 65 件の乖離も同時解消。`name` は全件 field 優位と実測済みなので情報は減らない。実装は +15 行程度

## 8. 取込器側の是正 — **不要**

現行の取込経路 `scripts/import-projects.ts` は **body を生成していない**（`projects-import-YYYY-MM.json` に手書きされた `it.body` をそのまま渡すだけ・226 行を確認）。
テンプレを生成するコードはリポジトリに**現存しない**。

createdAt の分布がこれを裏づける:

| 月 | テンプレ保持 | 非保持 |
|---|---|---|
| 2026-05 | **179** | 84 |
| 2026-06 | 0 | 15 |
| 2026-07 | 5 | 1 |
| 2026-08 | 0 | 46 |

**2026-05 の一括取込がほぼ全て**。以後の取込はキュレーション本文。
→ **新規混入の心配はない。是正すべきは過去分だけで、それは §3 の表示時再構成で足りる。**

ただし再発防止として、受け入れ検査に 1 行足すことを提案する:
「新規 POST の body が固定見出し `h3af4d147a9` で始まっていたら落とす」（#118 の `verify:grid-fields` と同型）。

## 9. ★破損の機序は 3 種類ある（走査レポート §F の恒久策に追記）

一次照合で、これまで把握していた 2 種に加えて **3 種目**が見つかった。

| # | 機序 | 例 | 見分け方 |
|---|---|---|---|
| 1 | PR タイトルを「…市」で切り出す | `pr-tecra-miyagi`「【想定年利12.0%】…「宮城県角田市」 | 記号・長さ・英数字で検出可 |
| 2 | 発表企業の本社所在地を設備所在地に混入 | `energia-first-bess`「広島県内」（中国電力の本店＝広島市）／`pr-co143072-bess-2`「東京」（東京センチュリーの社名・本社） | **機械検出が難しい**。県名として正常なので長さ・記号では引っかからない |
| 3 | **★新種: 大字からの部分文字列** | `pr-co169829-bess`「奈良」← 一次「埼玉県熊谷市**上奈良**」。リリース全文に「奈良県」は **0回** | **さらに難しい**。県名と一致してしまうため、`prefecture` フィールドに入ると完全に正常に見える |

機序 2・3 は「値の見た目」では検出できず、**一次と突き合わせるしかない**。
走査レポートの (b) 検査（`prefecture` と本文の県名の突合）が機序 2・3 を拾える唯一の機械検査だが、
本文側にも同じ誤りが焼かれている場合は両方が一致してしまい**検出できない**という限界がある。
→ 恒久策としては §8 の受け入れ検査に加え、「`prefecture` と `city` の整合（その市区町村が本当にその都道府県に属するか）」を
市区町村マスタで検査するのが有効（機序 3 は市区町村側が正しいため、県との不整合として現れる）。
