# 一覧の並びが「参照元 API の登録順」に暗黙依存していた件（2026-08-31）

microCMS API 統合（industry-events → policy-events、11→10）で /events の並びが変わった。
データは正しく移っており、**集合・件数・日付表示はすべて不変**。変わったのは同着日のタイブレークだけ。
本書は原因と、採用した恒久策・以後の不変条件を残す。

## 1. 何が起きたか

工程6-b（切替前後の main 本文比較）で /events に差分が出た。

- 一覧の見出し数: before 41 / after 41、**集合は完全に同一**（欠落・追加ゼロ）
- **順序が違う位置: 11 箇所**。すべて**同一 eventDate 内での入れ替わり**
- 「直近の主要イベント（60日以内）」でも 2026-09-08 の3件の並びが
  `再エネEXPO大阪 → 電気学会 → RE+` から `RE+ → 再エネEXPO大阪 → 電気学会` に変化

| 位置 | before | after |
|---|---|---|
| 4/5 | NEDO 蓄電池技術シンポジウム 2026 | METI GX 投資サミット 2026 |
| 6/7 | 日本太陽エネルギー学会 シンポジウム 2026 | World Energy Storage Conference China 2026 |
| 10/11 | BATTERY JAPAN 2026 秋 | スマートエネルギーWeek 2026 秋 |
| 13/14 | 再エネEXPO 大阪 2026 / 電気学会 電力・エネルギー部門大会 2026 | RE+ 2026 / 再エネEXPO 大阪 2026 |

（残り3箇所も同型の同着日入替）

## 2. 原因

`client.getList({ queries: { orders: '-eventDate' } })` は **同一 eventDate の二次ソートを定義していない**。
タイは microCMS の内部順（実質は登録順）に落ちるため、一覧の並びが
**「参照元 API にレコードを登録した順序」に暗黙依存**していた。

統合で 41件を policy-events へ投入した順序（greedy set cover 順＝選択肢の検証を最短で終わらせる順）は
旧 industry-events の登録順と当然違うので、同着日の並びが入れ替わって表面化した。

データ側の欠陥ではない。移行の #106 照合は 41/41 一致・差集合空で、
**並びの決まり方だけが暗黙だった**。落とし穴 #121（同じ意味の値を2箇所で別々に算出しない／
「代表値」を配列の [0] から採らない）と同型で、こちらは「順序の代表」を内部順に委ねていた形。

## 3. 採用した恒久策（ユウ裁定: 案1）

旧 API の登録順は**再現しない**。これから削除する API の登録順に依存し続ける設計になり、
次に1件足した瞬間にまた崩れるため。代わりに決定的なタイブレークを置く。

```
第一キー : eventDate 降順（従来どおり。ここは変えない＝読者に見える本当の変更にしない）
タイブレーク: title（localeCompare('ja') 昇順） → slug 昇順
```

実装は `src/lib/microcms.ts` の `compareEventsForDisplay()` 1箇所に置き、
`getAllEventsRaw()`（統合後の唯一の fetch 経路）でソートしてから返す。
これにより **/policy-calendar と /events の両ビューが同じ規則**になる（#119: 正規化は一箇所）。

Gr11 の `/grid/search`（空容量降順 → 名称 → slug）と同じ「意味のあるキー → 名称 → slug」型に
揃えてあり、サイト全体で並びの決め方が統一される。

## 4. タイブレーク導入で並びが変わる件数（実測）

| ビュー | 件数 | 順序が変わる位置 | うち日付が変わる位置 | 同着日 |
|---|---:|---:|---:|---|
| /policy-calendar（kind 未設定 or 政策） | 54 | **11 箇所** | **0** | 7 日（最大3件同着） |
| /events（kind=業界） | 41 | **6 箇所** | **0** | 5 日（最大4件同着） |

※ /policy-calendar は統合の切替時点では before/after 完全一致だったが、
　 同着日を7日持つため、タイブレーク導入で11箇所が入れ替わる。いずれも同着日内のみ。

## 5. 以後の不変条件

- **イベント一覧の並びは `compareEventsForDisplay` だけが決める。** 呼び出し側で並べ直さない
- `orders` の第一キー（`-eventDate`）を変えるときは「読者に見える変更」として扱い、
  before/after の日付表示の差分を必ず報告する
- 同着日以外での順序変化が出たら**実装ミス**。停止して原因を特定する
- 新しい一覧を作るときは、ソート指定に**必ず決定的なタイブレークを置く**
  （内部順・登録順・`[0]` を代表にしない）
